StockForge

A standalone twin of Summit Gaming's real-time inventory engine, running on its own fake seeded shops instead of Summit's real database. It exists so I can show someone exactly how the real thing behaves - live, poke at it yourself - without ever pointing them at a real customer's data. It's also become my testbed: new e-commerce features get built and proven here first, before they ever touch Summit's live system.

The problem

Summit's real-time inventory engine (see the Live Inventory case study) is real client work, running on a real store's real data - not something I can just hand someone a login to. But "trust me, it's good" isn't proof of anything. I wanted a way to let someone actually use the real engine - scan an item, watch the stock sync live - without it ever being able to touch Summit's actual database. The honest answer was to rebuild it as its own system, on its own fake shops, isolated hard enough that "fake" and "real" data structurally cannot mix.

How tenant isolation actually works

The danger of any shared-database system is always the same shape: one forgotten tenant filter, buried in one route, leaking one shop's numbers into another's screen - or in this case, letting a demo visitor's poking-around ever reach real data. The fix isn't "remember to add the filter everywhere" - people forget. It's making the filter impossible to skip.

The engineering decisions

1. One choke point, not a convention.

Every tenant table read/write runs through a single repo class scoped to the caller's shop at construction time. There is no code path that skips it - "don't forget the filter" became "there's nothing to forget."

2. Real-time stays per-shop.

Summit broadcasts stock changes to everyone connected - correct for one store, a data leak for many. Here, every socket joins a room named for its tenant on connect; a stock change only ever reaches that one room.

3. Feature flags as an honest kill switch.

Every shop's enabled features live as one list - unset means "show everything" (so the default demo never regresses), an explicit list restricts to just those, enforced server-side on the actual mutating routes, not just hidden in the UI. That's what lets a half-finished feature exist in the codebase without ever being reachable until it's actually ready to show.

4. Offline is a real state, not an edge case.

The newest piece - a barcode-first counter screen - assumes the shop wifi will drop mid-sale. Scans resolve from a locally cached catalog with zero network round-trip; a sale made offline queues in IndexedDB, replays safely on reconnect (a retried request can't double-sell the same scan), and the screen never just... stops working because a connection blinked.

5. Small attack surface on purpose.

Hand-rolled sessions (HMAC-signed cookies, Node's built-in scrypt) and a hand-rolled security header set instead of a dozen npm packages. Fewer dependencies means fewer supply-chain surprises and a codebase I can actually audit end-to-end myself.

Proof of range

Nobody's paying for this yet, so I stress-test it myself: a seeded catalog of 1,500+ SKUs under one tenant to make sure search, stock math, and the register flow hold up past toy-demo scale, plus a from-scratch typo-tolerant search layer (partial matches, misspellings, special characters) that the original single-shop version never needed. It's the same standard I hold client work to, pointed at something nobody's asked me to build yet.

What's actually next

Whatever Summit's real backend needs next gets prototyped here first, on fake data, until it's boring and reliable - then it moves over. Right now that's the barcode-first counter workflow above; next up is whatever the real store actually runs into.

What's protected

Same policy as everything else here: this is the shape of the system and the decisions behind it, not the source. The isolation layer and the offline-sync protocol stay private - it's the reusable core I carry into every future build, not something I hand out.
